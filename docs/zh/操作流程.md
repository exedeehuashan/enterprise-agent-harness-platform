# EAHP 操作流程

本文按"要做一件事，依次点哪里"的方式，列出控制台的每个操作流程。功能说明见[用户手册](用户手册.md)，部署和配置见[运维手册](运维手册.md)。

- 控制台：<http://127.0.0.1:8088>
- 方括号里是需要的最低角色：〔查看者〕〔操作员〕〔审批人〕。
- 本地示例中被测项目是 online-shop。它的套件有 `backend-unit`、`backend-integration`、`frontend-unit`、`contracts`、`frontend-e2e`、`performance`；API 测试集有 `catalog-api-smoke`、`order-api-smoke`；临时环境模板是 `env-pr`。

## 总览：一次完整的质量闭环

```
登记项目 → 提交代码 / 开 PR → 自动运行套件 → 失败分析（AI）
        → 代码智能体修复 → 审批 → 草稿 PR + 验证运行 → 人工审阅合并
        → 发布门禁 PASS → 生成 QA 报告 → 发布
```

下面每一节对应其中一步或一项日常操作。

---

## A. 入门

### A1. 登录

**方式一：API 令牌**

1. 打开控制台，在登录页的 **API 令牌** 框里粘贴令牌。
2. 点 **登录**。

令牌只保存在当前标签页，关掉标签页后需要重新登录。

**方式二：单点登录**（部署时用了 `EAHP_SSO=on`）

1. 点 **使用单点登录**，浏览器会跳到 Keycloak 登录页。
2. 输入账号和密码。本地测试账号有三个，密码在 `sso/generated/dev-users.txt`：
   - alice：审批人
   - bob：操作员
   - carol：查看者
3. 登录后自动回到控制台，右上角显示 `sso:alice`。
4. 登录过期（约 5 分钟到 1 小时，由 IdP 决定）后需要重新登录。

### A2. 切换语言

点右上角（登录页也有）的 **中文 / English**。选择会记在这个浏览器里。

### A3. 退出

点右上角的 **退出**。用单点登录登录的，退出时也会结束 Keycloak 的会话，下次点 **使用单点登录** 需要重新输入账号密码，可以换成其他用户。用令牌登录的，关掉标签页也等于退出。

## B. 任务和运行

### B1. 创建任务〔操作员〕

1. 打开 **任务** → **新建任务**。
2. 填写 **标题** 和 **描述** → **创建任务**。
3. 任务列表可以按 **状态** 筛选，并分页查看。

任务是一组运行的容器，一个任务里可以放多次测试运行、API 测试和代码智能体运行。

### B2. 运行测试套件〔操作员〕

1. 打开一个任务 → **运行测试套件** 标签。
2. 依次选择或填写：
   - **项目**，例如 online-shop；
   - **分支、标签或提交**，例如 `main`；
   - **套件**，例如 `backend-unit`；
   - **套件来自**：可以选"在仓库中，登记的套件作为后备"，也可以选"只用登记的套件"；
   - **超时（秒）**。
3. 点 **运行套件**。
4. 点开新出现的运行，进入运行页面。如果套件需要 Docker（标有"需要 Docker（需审批）"），运行会停在"等待审批"，见 C1。
5. 运行结束后，在运行页面查看：
   - **测试结果**：测试数、失败、错误、跳过、耗时、覆盖率；
   - **失败的测试**：每个失败附带**类别**和**历史**（最近 N 次中失败几次、上次通过于哪个提交）；
   - **失败原因**：例如"环境：Docker"或"断言失败"；
   - **产物**：可以 **下载** 报告压缩包，并附有 SHA-256；
   - **审计记录**：谁在什么时候做了什么。
6. 运行中可以点 **取消运行**。

### B3. 运行 API 测试〔操作员〕

前提：项目已经登记了测试环境（见 E3），或者使用临时环境（见 E4）。

1. 打开任务 → **运行 API 测试**。
2. 选择 **项目**、**分支、标签或提交**、**测试集**（例如 `catalog-api-smoke`）和 **环境**。页面会提示"请求发送到 …"。
3. 点 **运行 API 测试**，结果和 B2 一样显示在运行页面。

### B4. 请求计划并执行〔操作员〕

1. 打开任务 → **计划** 区域 → **请求计划**。模型会根据任务描述拆出步骤，每一步写明工具、版本、目标和超时。
2. 检查计划，没问题就点 **执行计划**。
3. **计划执行** 列表显示每一步的状态。需要审批的步骤会显示"有步骤在等待审批"。

---

## C. 审批

### C1. 批准或拒绝运行〔审批人〕

1. 打开 **审批**，这里列出所有等待中的运行。
2. 点运行编号进入运行页面，核对以下内容：
   - **输入摘要**：批准只对这一组输入有效；
   - **参数**：提交、套件、镜像、命令；
   - **到期**：超过这个时间未处理会自动过期。
3. 回到审批页，点 **批准** 或 **拒绝**。拒绝前会确认一次，运行以 REJECTED 结束。
4. 勾选 **显示已处理** 可以查看历史审批，包括决定人和时间。

下列操作都需要审批：

- 需要 Docker 的套件；
- 代码智能体；
- 临时环境；
- 自动修复。

## D. PR 自动测试

### D1. 让 PR 自动触发测试〔审批人配置，之后自动运行〕

前提：运维已经设置 `EAHP_GITHUB_POLL_ENABLED=true` 和 `EAHP_GITHUB_TOKEN`。

1. 打开 **测试项目** → **管理 online-shop** → **PR 触发器**，为需要的套件打开触发器。
2. 在 GitHub 上开一个 PR，或者向已有 PR 推送新提交。
3. 大约 1 分钟内，**PR** 页面会出现这个 PR 和触发的运行。页面会显示：
   - **触发方式**：完整运行，或只运行受影响的模块；
   - 跳过的原因，例如来自 fork，或改动不影响这个套件。
4. 点 **影响分析** 可以查看：
   - 改动文件；
   - 受影响模块，以及原因（改动本身，或依赖了改动）；
   - 在范围内的测试类。

支持 Maven、Gradle、npm 和 pnpm 工作区。

### D2. 把结果写回 GitHub〔审批人〕

前提：运维已经设置 `EAHP_GITHUB_WRITE_TOKEN`。

1. 打开 **测试项目** → **GitHub 回写** → **开启**。
2. 此后每次 PR 运行结束，GitHub 上会出现：
   - 提交状态（✓ 或 ✗）；
   - 一条汇总评论，每个 PR 只有一条，内容会随新结果更新。
3. **最近的 GitHub 调用** 列出每次回写的结果，用来排查问题。

## E. 测试项目配置

### E1. 登记新项目〔审批人〕

1. 打开 **测试项目** → 底部 **登记项目**。
2. 填写：
   - **标识**，例如 `online-shop`；
   - **名称**；
   - **默认分支**；
   - **仓库地址（https）**；
   - **允许的运行镜像**，每行一个。
3. 点 **登记项目**。
4. 在仓库里提交 `.eahp/qa-suites.json` 声明套件。也可以在 **管理 {项目}** → **添加或替换登记的套件** 里直接登记。

### E2. 修改策略、门禁和套件〔审批人〕

打开 **测试项目** → **管理 {项目}**：

- **项目和策略**：
  - 最长时间；
  - 是否 **允许访问 Docker**；
  - 是否 **允许外网访问**；
  - 改完点 **保存策略**。
- **发布门禁**：
  - **必需套件**；
  - **最低行覆盖率**；
  - **最低新代码覆盖率**；
  - **性能限制**（p95、错误率、变慢幅度）；
  - 改完点 **保存门禁**。全部留空表示删除门禁。
- **添加或替换登记的套件**：
  - 镜像；
  - 命令，每行一个参数，不经过 shell；
  - 报告目录；
  - 网络；
  - 是否需要 Docker；
  - 改完点 **保存套件**。
- **变更历史**：每次修改的人、时间和前后对比。

### E3. 登记测试环境（UAT 等）〔审批人〕

1. 打开 **测试项目** → **环境**。
2. 填写 **标识**、**名称**，以及每个服务的地址，例如 `catalog-api → https://uat.example.com`。
3. 点 **保存环境**。之后在运行 API 测试和性能测试时就能选择这个环境。

### E4. 按提交启动临时环境〔操作员发起，审批人批准〕

前提：仓库里有 `.eahp/environments.json`。online-shop 已经提供了模板 `env-pr`。

1. 打开 **测试项目** → **按提交的临时环境**，输入分支或提交。
2. 二选一：
   - **在新环境上运行测试**：启动环境，跑模板里列出的 API 测试，结束后自动销毁；
   - **启动环境**：环境保留到存活时间结束（例如 60 分钟），期间可以在 B3 里选它来跑测试。
3. 在 **审批** 页面批准（见 C1）。
4. 列表显示环境的状态和到期时间。提前结束点 **停止**。

### E5. 定时或按分支变化运行〔操作员〕

1. 打开 **测试项目** → **计划**。
2. 填写：
   - **套件或 API 测试集**；
   - **环境**（仅用于 API 测试）；
   - **分支/提交**；
   - **时间**：选"分支有新提交时"，或"按计划（UTC）"再填 **Cron 表达式**（秒 分 时 日 月 周，例如 `0 0 2 * * *` 表示每天 02:00 UTC）。
3. 点 **添加计划**。已有的计划可以 **暂停**、**恢复** 或 **删除**。

### E6. 用 AI 生成 API 测试〔操作员〕

1. 打开 **测试项目** → **AI 生成的 API 测试**。
2. 填写：
   - **OpenAPI 文件**：仓库里的路径；
   - **服务**；
   - **分支/提交**；
   - **重点**（可选），例如"只测下单失败场景"。
3. 点 **用 AI 生成**。草稿会先经过校验，无效的草稿会标为"无效"。
4. 有效的草稿可以直接在某个环境上运行，也可以 **下载** 后提交到仓库的 `.eahp/api-tests.json`。

## F. 质量看板和发布

所有操作都在 **质量** 页面完成，先在顶部选择 **项目** 和 **时间范围**（最近 7–90 天）。

### F1. 看整体质量〔查看者〕

- 顶部卡片显示 **通过率**、**失败的测试**、**不稳定测试** 和 **门禁**。
- 每日通过率的小图可以切换成 **表格**。
- **当前失败**：现在仍在失败的测试，以及持续失败了几次运行。
- **不稳定测试**：同一提交上结果不一致的测试。
- **最慢的测试**：平均耗时最长的测试。

### F2. 发布前检查门禁〔查看者〕

1. 在 **发布门禁** 输入分支、标签或提交 → **检查门禁**。
2. 结果有三种：
   - **PASS**：可以发布；
   - **FAIL**：逐条列出原因，例如某套件失败、覆盖率不足、p95 超限；
   - **PENDING**：还有必需的套件没跑完。
3. 点 **QA 报告** 生成 Markdown 报告，再点 **复制 Markdown**，就可以贴到 PR、邮件或发布单里。

### F3. 对比两个提交〔查看者〕

1. **对比提交** → 填写 **基准**（例如上一个发布标签）和 **目标** → **对比**。
2. 结果列出新增失败、已修复、仍在失败、新增测试和已删除测试，每个测试都能看到细节。

### F4. 检查新代码覆盖率〔查看者〕

1. **覆盖率** 区域会显示行覆盖率和分支覆盖率的趋势。
2. 填写 **基准**、**目标** 和 **套件** → **检查改动行**。
3. 结果显示改动行的覆盖率和门禁要求，并列出每个文件**未覆盖的行号**。

### F5. 看性能〔查看者〕

**性能** 区域显示每次 k6 测试的 p95 延迟、错误率、每秒请求数和总请求数。趋势图上有门禁限制线。

### F6. 隔离不稳定测试〔审批人〕

**方式一：采纳 EAHP 建议**

1. **被隔离的测试** → **EAHP 建议**。每条建议都附有证据：在多少天内、多少个提交上，同一提交既通过又失败，以及最近一次失败的信息。
2. 点 **隔离 14 天** 采纳；或者填写理由后点 **驳回**。

**方式二：手动隔离**

1. 在 **失败的测试** 中选一个测试，填写 **天数**（最长 30 天）和原因。
2. 点 **隔离**。

被隔离的测试失败时不会阻断门禁。到期自动解除，也可以提前点 **解除**。

## G. 失败分析和自动修复

### G1. 用 AI 分析失败〔操作员〕

1. 打开一次失败的运行 → **用 AI 分析**。
2. 分析结果包括：
   - 可能原因；
   - 类别；
   - 置信度（低、中、高）；
   - 证据引用；
   - 下一步建议；
   - 消耗的 token 数。
3. 分析结果只供参考，平台不会根据它自动执行任何操作。

### G2. 让代码智能体修复这次失败〔操作员发起，审批人批准〕

前提：运维已经配置 `ANTHROPIC_API_KEY`，构建好代码智能体镜像，并在 H5 登记了允许推送的仓库。

1. 在失败的运行页面点 **用代码智能体修复**。只有代码缺陷类失败才会被接受，环境问题会被拒绝。
2. 审批人在 **审批** 页面批准。
3. 等待代码智能体运行，通常需要几分钟。完成后会依次出现：
   - **代码智能体运行**：可以查看 diff 和日志；
   - **草稿 PR #N**：链接到 GitHub；
   - **验证运行**：在 PR 提交上重新跑同一个套件。
4. 验证结论有三种：**已修复**、**部分修复**、**未修复**，附带修复几个、仍失败几个、新增失败几个。同样的结论也会写成 PR 评论。
5. 在 GitHub 上审阅草稿 PR，决定是否合并。EAHP 从不自动合并。

### G3. 开启自动修复〔审批人〕

1. **质量** → **自动修复** → 勾选 **对每次失败的运行提出修复**。
2. 此后每次失败的运行会自动提出修复，但每个请求仍需在 **审批** 页面批准。每个项目每天最多 3 个。

### G4. 直接给代码智能体提修改要求〔操作员〕

1. 打开任务 → **代码智能体**。
2. 填写：
   - **仓库**；
   - **分支、标签或提交**；
   - **给 Claude Code 的指令**，例如"给 OrderService 的金额校验补单元测试"；
   - **最大轮数** 和 **超时**。
3. 点 **提交修改要求**，然后等审批人批准。仓库允许推送时，会推分支并开草稿 PR；否则只记录 diff。

## H. 管理〔审批人〕

都在 **管理** 页面。

### H1. AI 模型和用量

查看当前的提供方和模型，以及今天已用和每日预算。更换模型需要运维修改 `.env`，见运维手册第 3 节。

### H2. AI 评测

1. **AI 评测** → **运行评测**。用 12 个固定用例检查失败分析、计划和测试生成的质量，会消耗真实 token。
2. 结果显示得分、使用的模型、评测集版本和 token 用量。换模型或改提示词后都应该跑一次。

### H3. 业务模块开关

**业务模块** → 对某个模块（例如方案 4）点 **关闭** 或 **开启**。关闭后，这个模块提供的工具全部停用，不能再发起它的运行；重新开启即可恢复。

### H4. 通知

1. **通知** → 填写 **名称**，选择类型（Webhook、钉钉、企业微信、飞书、Slack 或邮件），然后填写：
   - **发送到**：地址或收件人；
   - **事件**；
   - **签名密钥**（可选）。
2. 点 **添加**。如果生成了签名密钥，它只显示这一次，请妥善保存。
3. 点 **发送测试**，确认能收到消息。
4. 状态显示"正常"或"失败中（连续 N 次）"。可以 **暂停**、**恢复** 或 **删除**。

### H5. 代码智能体仓库

1. **代码智能体仓库** → 填写 **标识**、**名称**、**仓库地址** 和 **默认分支**。
2. 勾选 **允许推送** 后，代码智能体会推分支并开草稿 PR；不勾选则只记录 diff。
3. 点 **保存仓库**。

### H6. API 令牌

1. **API 令牌** → 填写 **名称**、**角色**、**天数** 和 **描述** → **签发令牌**。
2. 令牌只显示这一次，请复制后安全地交给使用者。
3. 列表显示每个令牌的最近使用时间和到期时间。不再使用的令牌点 **吊销**。

### H7. 存储和保留

**存储和保留** 显示现存产物、已过期产物和表大小。系统每晚 03:30 UTC 自动清理，也可以点 **立即执行保留策略** 马上清理。

### H8. 备份恢复演练

**备份恢复演练** → **立即演练**。演练会把最新备份恢复到一个临时数据库并校验，结果显示结构版本、导出大小和恢复的行数。系统每晚也会自动演练一次。

## I. 运维命令（在服务器的仓库根目录执行）

部署或升级（会先自动备份）：

```bash
scripts/deploy.sh
```

带单点登录部署：

```bash
EAHP_SSO=on scripts/deploy.sh
```

首次准备本地 Keycloak 和测试用户：

```bash
scripts/sso-dev.sh
```

构建代码智能体镜像：

```bash
scripts/build-code-agent.sh
```

用最新备份做恢复演练（不影响生产库）：

```bash
scripts/restore.sh --drill
```

查看服务状态：

```bash
docker compose ps
```
